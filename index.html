Coconut is betting that context outlives the tool

Coconut AI sells a shared, governed context layer that every AI tool in an organization draws from. The thesis is sound and unusually well validated. Ten days after this report first ran, a second documentation site appeared describing a different product on a different architecture — no VMs, no git, Postgres and pages — and the marketing site still links to the old one. The thesis holds. The engineering underneath it has been replaced.

01 — The product

One company, two products, both documented

The marketing site sells a shared context layer: connectors, five context layers, a permission-aware MCP endpoint. The documentation at docs.coconut.md describes something else — Coco, "a solution platform built on pages": org, space, page, metadata, one agent per space. Both were live on 18 August 2026, and the coconut.dev nav still links to the older one.

The finding this revision turns on

The First-hand tab attached the shipped MCP connector on 9–10 August and found a surface matching no published documentation. docs.coconut.md documents exactly that connector. So every claim built on the older docs — VM per instance, git-versioned .nut/, the knowledge/context split — described a product Coconut publishes docs for and does not appear to ship, and is retired rather than quietly corrected.

What is actually differentiated

The distinction against enterprise search still holds — search helps people find information; a context layer gives AI the knowledge to act on it — but the mechanism changed. This is no longer a retrieval story. It is a query story: the difference between "which pages mention diligence" and "which pages are in diligence with conviction above 0.7, ranked."

Metadata as a query surface

Values are any JSON. set upserts, append extends arrays atomically, appendUnique makes re-running agents idempotent. Per-key audit trail, and changing a key never creates a page revision.

eq neq exists missing gt gte lt lte contains, AND-ed, with orderBy.

Views — the same engine, for humans

/views is a filter builder over the identical engine agents use. The whole view state lives in the URL, so a tuned query is a shareable link and a team dashboard.

Humans and agents on one query engine is the strongest structural idea in the product.

Agents as scoped principals

Scheduled runs execute as the space agent principal — write at home, read-only across org-visible spaces, nothing in other private ones. Manual runs carry the requesting user's authority.

A real permission design, not a label.

None appear in the older documentation or on the marketing site. Together they are most of a platform, and they arrived without announcement.

The five layers are marketing-only

Identity, Domain, Process, Relationships, State — the taxonomy the whole platform page is built around — appears nowhere in the new documentation. No layer field, no layer API, no mention in the object model. The shipped organizing principle is org → space → page, and the closest thing to a layer is a metadata key you chose yourself. That reframes the taxonomy from product architecture to sales narrative. It is a good sales narrative. It is just not what the software does.

Still unresolved after ten days

Layer 02 is Domain on the platform page and Product in the FAQ. Both were live on 8 August and both are still live on 18 August. For a company whose pitch is that inconsistent context produces inconsistent answers, ten days is a long time to leave two names on one layer.

Governance: the gap did not move

Propose-then-publish review

Still Coming soon on the platform page, and absent entirely from the new documentation — no review endpoint, no proposal object, no approval state on a page. Tiered propagation is the load-bearing beam of the governance pitch and the wedge against both free open source and the platform incumbents. Two doc sites, ~57 monitored controls and five verticals shipped ahead of it.

Pricing and security

Team / Company / Enterprise, contact-sales only — unchanged since 8 August, and still not the Starter / Growth / Enterprise older research recorded. The security page now describes two deployment models, managed or self-hosted, down from three.

SOC 2 — the one thing that moved in the right direction

On 8 August no SOC 2 claim appeared anywhere on the site. There is now a Vanta-backed Trust Center, linked from the main nav, with roughly 57 continuously monitored controls across five categories, all passing, last synced hours before this was read. The qualifier matters: the only downloadable artifact is an engagement letter — an audit begun, not a report issued, and Type II needs an observation window that cannot have closed. SOC 2 in flight and visibly instrumented is a far better answer to an enterprise buyer than silence, and still not a certificate. Dust and Mem0 both advertise completed Type II.

02 — Architecture

The VM reading was right about the docs and wrong about the product

On 8 August this report claimed a "Coconut" is not a database row but a provisioned virtual machine running an agent loop. The new documentation contradicts it in one clause — pages are versioned in Postgres as append-only revisions, "no git lifecycle" — and the claim is retired.

What the August reading got right, and what killed it

It was sourced correctly — skills docs defining a Coconut as "a VM with the nut CLI installed," a dialog asking for CPU, RAM and disk, both still live and still saying that. What did not exist on 8 August was any document describing the alternative. There is now, and it describes a conventional two-tier web app. The conclusion is not that the earlier analysis misread its sources; it is that Coconut publishes documentation for a product it does not ship — a worse fact about the company than a wrong diagram is about this report.

Retrieval is documented now, and the answer is Postgres

August's third architectural risk was that retrieval was undocumented while Hyper published query expansion, reciprocal rank fusion over embeddings and full-text, and a ZeroEntropy reranker — and that an evaluator would notice which company showed its work. Coconut has now shown its work: Postgres full-text search over title, path, content and frontmatter, ACL-filtered per hit. No embeddings, no vector store, no reranker, no hybrid fusion. The docs draw the line themselves — full-text answers "which pages talk about X", metadata answers "which pages are in state X", and you compose them.

Two ways to read this, and the second is more interesting

The uncharitable read — a company selling itself as the knowledge substrate for enterprise AI ships 2005-era retrieval, and any evaluator running a semantic query against a corpus that does not share its vocabulary finds out inside an hour.

The charitable read, which the documentation actually supports — Coco is not competing on retrieval and has stopped pretending to. The bet: most enterprise questions are state questions, not semantic ones; a typed, audited metadata layer answers them exactly rather than probabilistically; and FTS only has to be good enough to find candidates. If that is right, the RAG pipelines Coconut gets compared to are solving a problem the customer did not have. A genuinely defensible position — and one nobody at Coconut has written down.

Three revised architectural risks

The August list — VM cost per tenant, runtime lock-in, undocumented retrieval — is entirely superseded. What replaces it:

Risk 01

Two products is a tax on everything. Two doc sites, two object models, two MCP surfaces, two mental models for support to hold. Any prospect who finds both — and the marketing nav points at the losing one — has to be told which is real. That conversation never helps.

Risk 02

One agent per space is a hard ceiling. It makes permissions clean and it makes the space the unit of automation. It also means a team wanting two differently-scoped automations must split the space, dragging ACLs and page paths with it. Structure gets shaped by the automation model rather than the work.

Risk 03

FTS-only retrieval is undefended in public. The position is defensible; the defence is unwritten. Until someone publishes "why we did not build RAG," every technical evaluation scores it as a missing feature rather than a deliberate choice.

Given how critical the rest of this report is, it is worth saying plainly: the parts of Coco that are written down are written down well — secrets encrypted under a required key with a hard 503 rather than a silent plaintext fallback, idempotent ordered migrations, an SSRF guard that logs and refuses to retry. The problem is not quality. It is that the company publishes two truths and points customers at the older one.

03 — Workflows

The loop stopped being a feature and became three primitives

The older documentation shipped named loops — Daily Research Brief, Competitor Intelligence Loop, POV Voice Loop — recipes you switched on. The new documentation ships no loops at all: a scheduled task, a metadata query and a webhook, and you assemble the loop. That trades a ready-made demo for composability, and the docs never argue the trade.

Getting in — the demo gate is no longer the only door

On 8 August the only path was a sales call: invite-only, demo-gated, six steps to first value. The new documentation describes two paths that skip it, and the marketing site mentions neither.

Path A — a template installs the whole space

"Use this template" creates a space with pages, templates and agent instructions in place, and a marketing link can deep-link one straight through sign-in. A self-serve activation funnel, built and documented, on a product still sold as invite-only.

Path B — run it yourself in fifteen minutes

pnpm install, ./scripts/compose-local.sh up: Postgres, API, app, migrated and seeded. Written from a checkout, not a signup — specs/, ROADMAP.md, packages/db/drizzle/. Whoever these docs are for already has the source.

The read path

Same shape, different mechanism: the connector no longer assembles five context layers, it resolves pages and runs metadata queries. What comes back is the same grounded, sourced draft.

The write-back path has no gate on it

The correction loop, as actually shipped

In August, a user who spotted an error opened a Task — a change proposal an owner reviewed before it propagated. In the new object model there is no proposal object: no review endpoint, no approval state, no pending-change list. A correction is a PUT with an If-Match header, and if your ETag is current it lands.

Instead there is complete reconstruction after the fact: append-only revisions, a per-key metadata audit trail, make-latest, and a webhook the moment anything changes. Catch it in review, or catch it in the log — and for most teams the log is how wikis honestly work anyway. It is not the tiered propagation the platform page sells, and that distance is where an enterprise governance deal is won or lost.

Automation: a task is a page, a schedule is frontmatter

No separate job system: the agent's entire configuration is pages under a reserved agents/ prefix, so instructions and schedules are versioned, ACL'd, diffable and exportable like everything else. An elegant collapse.

PageWhat it is
<space>/agents/instructionsThe persona, layered into every run
<space>/agents/<task>A task. schedule, scheduleTz, scheduleEnabled live in its frontmatter — cron as a document property
<space>/agents/runs/<task>/<run-id>A run record — status, output, usage. Written by the run itself

The detail worth stealing

Scheduled runs execute as the space agent principal; manual runs execute with the requesting user's authority. The same task has different reach depending on who started it — an unattended 3am run cannot touch anything the agent was not granted. Most agent platforms have one identity and hope. This is the correct design, and it is one line in the docs.

The integration surface replaced the CLI

August flagged a "hidden second product": nut init, git worktrees, WebSocket terminals, code sessions, image and video generation — a coding-agent platform inside a knowledge product, with no buyer named for it. None of it survives. What replaced it is narrower and far easier to sell: four signed webhook events, a markdown-native HTTP API, and portable space bundles. If cutting the scope that had no buyer attached was deliberate, it is the best decision visible in this revision.

Push

page.created, page.updated, page.deleted, page.metadata.updated — the last carrying changedKeys. Signed sha256=…, three retries, full delivery log. Personal spaces never emit.

Pull

Same URL serves a human and a machine — Accept: text/markdown or a .md suffix. ?version=n reads history. No separate content API to drift out of sync.

Move

GET /spaces/:slug/export yields every page you can read. Paths are space-relative, so a bundle from deals imports into pipeline. Revision history stays home.

05 — Existential threat

What actually kills this company

Not Glean. Not the YC cohort. Two of the five threats below moved materially in ten days — one down, because Coconut cut the surface that caused it, and one up, because the company is now maintaining two products at once.

Threat 1 — The Anthropic dependency shrank

August's version rested on distribution: skills shipped through the Claude Code plugin marketplace, written to Anthropic's SKILL.md spec, with an unaffiliated third-party tool as the only route into Cursor or Codex. The new product has no skills, no marketplace and no SKILL.md — that supply-chain dependency is gone. What remains is real but ordinary: MCP is an Anthropic-authored standard, and Anthropic sells a product one layer up whose every improvement narrows the gap Coconut sells into. The same exposure every MCP-native company carries. Severity down from medium-high.

Threat 2 — The free option is good, and its author funds the competition

GBrain is MIT-licensed, Markdown-first, git-versioned, ships as an MCP server, has a multi-user company-brain mode, reportedly runs a 25-person brain for under $100 a month, and has 28,015 stars four months after creation. Written by Garry Tan — president and CEO of the accelerator that funded Hyper, Cerenovus, Savant, Memory Store and Glen.

A free, credible baseline does not have to win to hurt — it makes every paid product justify its delta at the start of every sales call. Coconut's honest delta is managed connectors, permissions enforced for you, deployment options, someone to call at 2am: the answer GitLab gives against self-hosted git. It prices Coconut against the engineering cost of the alternative rather than the value of the context. Much lower ceiling.

And the new documentation makes this harder, not easier

Docs written from a checkout — pnpm install, specs/, ROADMAP.md, Helm, Terraform — invite exactly the comparison Coconut least wants. A buyer who can read a Compose file and a Postgres schema can price building it. The self-host story wins security reviews and loses pricing power, and Coconut now leads with it.

Threat 3 — Governance is the wedge, and the wedge is still not finished

Governance is the one defensible position Coconut has chosen against platform-native memory, free open source and capture-first tools, and it is the right choice. Ten days on, propose-then-publish review is still absent — not merely "coming soon" on the platform page, but missing from a freshly written 27-page object model that found room for webhooks, a template gallery and SCIM.

The compliance half improved: ~57 monitored controls is a real answer where there was silence. But better-funded competitors are on the same hill — Glean's permissions-aware knowledge graph, Stack Internal's MCP over verified knowledge, Guru's years of verification workflows — and the fortification Coconut built last is the one its own marketing leads with.

Threat 4 — Two products, one team

In August this was breadth: a 2–10 person company shipping a Studio, control plane, iOS app, editor extension, CLI, REST API, MCP server, A2A endpoint, agent runtime, skills marketplace, mail, media generation, terminals and git worktrees. The new product deletes almost all of it — which should have retired this threat, and instead made it worse. Deleting a surface from documentation does not delete it from production, from support, or from customers already on it.

The three readings, and none of them is comfortable

A migration mid-flight — most likely, and it means every existing customer sits on an architecture the company has moved off, with a migration nobody has described publicly. A deliberate two-product strategy — a 2–10 person team maintaining two object models, two MCP surfaces, two doc sites. An abandoned line left standing — cheapest to execute, most corrosive, because the abandoned docs are the ones the marketing site links to. This report cannot distinguish between them on public evidence. Neither can a prospect.

Threat 5 — The name, and now the domains

"Coconut" already collided with Coconut Software (banking), Coconut tax software, coconut.co (video encoding) and a Meta research paper; Crunchbase and PitchBook return the wrong companies. That was a search tax. The new footprint adds a comprehension tax — six hostnames across two top-level domains, where the TLD, not the subdomain, tells you which product you are reading about:

Verdict — revised 18 August 2026

The thesis is unchanged and still validated: "Enterprise Context & Data Governance Layer for AI" ranks HIGH in the companion stack report — $5–10B TAM, #2 opportunity across all tiers. What changed is that the product underneath it has been replaced, and the replacement is better: narrower, cleaner, self-hostable, with an honest query engine where there was a vague retrieval claim and none of the scope that had no buyer attached.

The engineering judgement is good. Cutting the CLI, terminals, media generation and git surface was right; collapsing agent configuration into versioned pages is elegant; the webhook security posture beats most Series B products.

The failure is entirely in the telling. A company whose product is one consistent, governed source of truth is currently publishing two contradictory documentation sites, pointing customers at the wrong one, and describing on its marketing site a five-layer architecture its software does not implement. That is not a positioning nitpick. It is the product's own thesis, failing in public, on its own website.

The four questions worth putting to the founder

  1. Which product is real, what happens to customers on the other one, and when does the marketing nav point at the right docs?
  2. What is the plan for the day Anthropic ships governed org context in Cowork?
  3. Why no vector retrieval — is that a deliberate bet on state-over-semantics, and if so why has nobody written it down?
  4. When do propose-then-publish review and an actual SOC 2 report land? The engagement letter is up; the report is the thing buyers ask for.

Which is validation and warning in one sentence: a HIGH rating on a widely-read map means the opportunity is legible to everyone, and roughly a dozen teams read it the same way in the same twelve months.

The robotics stack — the honest answer is no

Every software layer in that 14-layer map is defined by physical embodiment — motion planning, real-time safety runtimes, world models, certification — and Coconut has neither an embodied component nor a robotics data model. Two adjacencies, stated rather than stretched: a fleet-ops team has exactly Coconut's governance problem, which makes Coconut a buyer-side tool for that team, not a component of the stack; and the robotics-native version already exists in Osseus (YC S26), connecting CAD, schematics, BOMs and firmware in permissioned version-aware memory. Entering would need BOM-aware connectors, not Slack and Drive.

Recommendation, revised: place Coconut at L10, cross-referenced to L11 only, and leave the robotics map alone. Drop the L09 cross-reference — the surface that justified it is gone from the product. Ten days made Coconut's stack position narrower and more accurate, which is the better outcome: a context layer that claims to be everywhere is indistinguishable from one that is nowhere.

Finding 2 — The real object model

Three layers of content per page, not one — the detail that makes "prose carries judgment, metadata carries the facts that churn" actually work.

Finding 3 — Several things are better built than the marketing claims

Worth telling the founder plainly: the engineering is ahead of the story being told about it.

What the connector showedThe detail no marketing page explains
Metadata patches create no page revisionset upserts (JSON null deletes), append extends arrays atomically, appendUnique is idempotent — explicitly safe for re-running agents. Metadata carries its own audit trail, separate from page versions. Exactly the right design for "prose carries judgment, metadata carries the facts that churn."
Real optimistic concurrencyEvery update asserts a version; the second concurrent write fails rather than winning. Corrected 18 Aug — the connector field was expectedVersion, the documented HTTP mechanism is If-Match/ETag with 412 on mismatch. Same guarantee, two surfaces; logged in the conflicts table.
The link graph is automaticIndexed from Markdown bodies on every write, with backlinks and broken-target flagging. A dependency map that maintains itself, never mentioned in the marketing.
Run observability is deepStatus, timing, model, token usage, turn count, output, and an opt-in structured transcript of reasoning and tool calls. Better instrumentation than most agent platforms expose.
Agents really are principalsA run executes as the space's agent principal and writes its own record. The permission story is architectural, not cosmetic.

Finding 4 — Credit exhaustion degrades quality invisibly

The one behavioural finding, and the most important thing on this page

When an organization exhausts its agent credits, agent_run_task cannot execute. Work does not stop — it falls back to running inline, in whatever client the user is holding, with no retrieval.

Its output is structurally indistinguishable from a fully researched run — same format, same confident tone, same citations-shaped prose, same gate tables. In the case observed, a run that performed zero web fetches made four specific, confident, false assertions about what pages on coconut.dev say, each independently checked and contradicted.

Two things make this severe rather than cosmetic:

  1. The quality gates cannot catch it. They interrogate reasoning — is the frustration real, is it genuinely unmet, is the scope honest. None asks whether evidence was actually retrieved, so a well-reasoned argument from fabricated premises passes every one.
  2. The signal to catch it exists and is unused. Run records carry a fetch count. Nothing consumes it. A run that fetched nothing may assert what a live page says.

The fix is small and in the product's own idiom: a run with zero retrievals should not be able to write a claim sourced to an external URL, and a degraded run should be marked on every page it touches. Provenance is what Coconut sells; this is the one place it is not enforced on itself.

In fairness, this is the degraded path, not the designed one. A properly executed run in the same instance — a hundred-plus tool calls, fetching live pages — recorded the same contested facts correctly. The architecture works; the failure mode is what happens when it cannot.

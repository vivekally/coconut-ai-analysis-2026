Set up Coconut for Coconut

A step-by-step guide to standing up a Coconut space where the company being modelled is Coconut, then running both published product loops against it. Everything below is copy-paste. The point is not just to configure the tool — it is to watch what it does when the honest answer is "I don't have enough to go on."

Company Coconut AI Inc. Seat Head of Product Loops Competitor Intelligence · Product Improvement Packs A public-facts · B synthetic Path App UI · HTTP API Steps 10

Read this before you paste anything

This guide ships two data packs. Pack A contains only publicly verifiable facts about Coconut. Pack B contains fabricated customer feedback, support tickets, and churn notes — invented so the Product Improvement Loop has a signal to work with, because by design it refuses to invent one itself.

Every Pack B file carries a warning header. Nothing in Pack B is real. No Coconut customer said any of it, and every company named in it is fictional. Load it into a test instance only, never quote it to anyone, and delete it when you are done.

The interesting part of this exercise

Run the Product Improvement Loop after Pack A and before Pack B. With only public facts loaded there is no concrete user signal, and the loop's own instructions say "Do not invent a signal." A correctly-built product files "No signal this run — context gap" and stops.

If it produces a confident proposal anyway, that is the single most informative result you can get from this evaluation — it would mean the discipline the product sells is not enforced in the product itself. Either outcome is worth knowing before you meet the founder.

Your buyer is a product or ops leader, not a developer — the honest test of "up and running in days, no blank screen" is the path that person would actually take. What changed for the better

The old guide had to warn you that there was no obvious place to put context — a context product where adding context was the least discoverable action. That is fixed: context is a page, pages are the whole product, and the "Start from" picker means you are not staring at an empty editor. The awkward step is now different, and covered in step 3: deciding what belongs in the body, what belongs in frontmatter, and what belongs in metadata.

01

Prerequisites

Sales is invite-only, so the fastest path is an org you already have access to. If you do not have one, the documented quickstart stands up the whole stack locally — and running it yourself is itself a useful data point on the self-host claim.

shell · optional — the local stack
pnpm install
./scripts/compose-local.sh up     # Postgres + API (8787) + app (3000), migrated and seeded
# then open http://localhost:3000 — seeded identity is demo@local in the demo space

For an org you have been given, you need a session in the browser and an agent key for the API blocks below. Every route in this guide is ACL-checked, so the key's reach is whatever space membership it has been granted — an agent gets read-only at org scope and needs an explicit membership to write anywhere.

Time this

"Up and running in days, no blank screen" is a core claim. Note how long you spend between here and the end of step 4 — you are an expert with prepared content, so treat your own elapsed time as the optimistic bound on a real team's.

Use a throwaway or clearly-labelled instance. Step 8 loads fabricated data. You do not want it mixed into anything you rely on.

02

Create the space

Create one space, slug coconut, visibility private. Everything in this guide lives inside it. A space carries its own members, its own visibility, and exactly one agent — that last constraint shapes the rest of the setup, so notice it now rather than at step 5.

Two reserved prefixes exist the moment the space does

agents/ holds the agent's instructions, task pages and run records; templates/ holds page templates. Both are hidden from listings and search — you address them directly. So the agent's entire configuration is versioned, ACL'd, diffable and exportable like any other page. That is the most elegant thing in the product and it appears nowhere in the marketing.

http · confirm the space and your reach
export COCO=http://localhost:8787          # or your org's API host
export KEY=dev-agent-key-change-me         # your agent key

curl -s "$COCO/spaces" -H "Authorization: Bearer $KEY"
curl -s "$COCO/spaces/coconut/pages" -H "Authorization: Bearer $KEY"

Use a throwaway or clearly-labelled space. Step 8 loads fabricated data. Keep it private so it stays out of org-wide search — and note that personal spaces never emit webhooks, so if you want step 10's webhook to fire this must be a real space, not your personal one.

03

Pack A — context documents

Pack A Public facts and role configuration only. Safe to keep.

Four pages define who the agent thinks it is: context/role, context/team, context/agents and context/memory. Paths nest, so these sit together without needing their own space.

These describe seats, not real people — Coconut does not publicly name its leadership, and this guide does not invent names for them.

App route, and the one judgement call this product asks of you

New page, path context/role, paste, save. Repeat for the other three. No commit step, no directory layout to learn.

Three places can hold a fact and they behave differently. The body is narrative and every edit writes a revision. Frontmatter travels with that revision. Metadata sits alongside, is queryable across pages, and changing it creates no revision but does write an audit event. Put judgement in the body and churn in metadata. Getting this wrong is the new onboarding tax — and it is a better tax than arguing about which of five layers a runbook belonged to.

context/role · who the agent is
__FILE__base/context-role.md__
context/memory · standing facts, dated
__FILE__base/context-memory.md__
▸ Show the remaining two context files (team.md, agents.md)
context/team · seats, not names
__FILE__base/context-team.md__
context/agents · standing rules
__FILE__base/context-agents.md__
http · or write all four from a terminal
# save the blocks above as role.md, team.md, agents.md, memory.md first
for p in role team agents memory; do
  jq -Rs --arg t "$p" '{title:$t, content:., frontmatter:{}}' < "$p.md" \
  | curl -s -X PUT "$COCO/pages/coconut/context/$p" \
      -H "Authorization: Bearer $KEY" -H "Content-Type: application/json" -d @-
done

# read one back as clean markdown — the same URL a human reads in the browser
curl -s "$COCO/pages/coconut/context/role.md" -H "Authorization: Bearer $KEY"

Note what that last line demonstrates: one URL, one resolver, one ACL check — a human gets rendered HTML, an agent gets clean markdown. Updating an existing page requires If-Match with the current ETag and returns 412 without it, so re-running this loop over pages that already exist fails rather than silently clobbering. That failure is the feature.

04

Pack A — knowledge base

Pack A Five documents, every factual claim traceable to a public source.

There is no separate knowledge type — these are pages like any other, at kb/<name>. kb/competitors-list is the editable input to the Competitor Intelligence Loop; the other four give the Product Improvement Loop enough to identify the product and respect its constraints.

Keep the paths exactly as shown, and seed metadata now

Both task prompts reference competitors-list, product, constraints and positioning by name. While you are here attach starting metadata to each — owner, last-verified, confidence — because step 10's view is only as good as the metadata seeded now. This is the step where the product's actual differentiator either gets used or does not.

That last call is the quiet good idea: a discoverable key namespace with usage counts, so writers converge on keys that already exist instead of inventing owner, Owner and owned-by. Check it again after step 6 — whether the agent converged on your keys or invented its own is a real test of the vocabulary discipline this product sells.

05

Define the space agent

There is no skills system and no job system. The space has one agent, defined entirely by pages: agents/instructions is the persona layered into every run, and each loop is a task page at agents/<task>.

One agent per space — plan for it

Both loops share one persona and one set of connector credentials. If you wanted the competitor loop to have web reach and the improvement loop not to, you could not express that here without splitting the space and dragging the ACLs and page paths with it. That is a real constraint, and worth raising with the founder. Attach a web-capable connector before step 6 — a research task with no reach produces a confident-sounding file built entirely from model priors, which is worth provoking deliberately once.

Paste context/agents from step 3 into agents/instructions, then create the two task pages below.

06

First run — Competitor Intelligence

Every competitor is a first-run, so this produces twelve full baselines plus the landscape overview. Expect it to be the slowest run you will do.

run · trigger it by hand, then inspect
# Run from the task page's Run control, or over MCP with agent_run_task.
# A manual run executes with YOUR authority — a scheduled one uses the agent principal.

curl -s "$COCO/spaces/coconut/pages" -H "Authorization: Bearer $KEY" | grep competitor
curl -s "$COCO/pages/coconut/kb/competitors.md" -H "Authorization: Bearer $KEY"

# the run record it wrote about itself
curl -s "$COCO/spaces/coconut/pages" -H "Authorization: Bearer $KEY" | grep agents/runs

What should exist afterwards

  • kb/competitor-<name> — twelve pages, each with a dated baseline under Product and pricing, Positioning, Funding and hiring, and Sentiment.
  • kb/competitors — one landscape overview, readable at a glance, ending with the "What this means for us" section the adapted prompt asks for.
  • Metadata on every competitor page: last-reviewed, threat-level, a sources array, and sources-fetched.
  • A run record under agents/runs/competitor-intelligence-loop/.

07

First run — Product Improvement (expect a gap)

This is the test

Only Pack A is loaded. There is no customer feedback, no support data, no churn note — nothing describing a specific user in a specific moment of friction. The task's own instructions forbid inventing one. The correct output is a page titled "No signal this run — context gap," with gate-status: context-gap in its metadata.

run · trigger it, then query the verdict
# the verdict is queryable without opening the page
curl -sG "$COCO/search/metadata" -H "Authorization: Bearer $KEY" \
  --data-urlencode 'filters=[{"key":"gate-status","op":"exists"}]' \
  --data-urlencode 'orderBy=confidence' --data-urlencode 'order=desc'

Read the result carefully

OutcomeWhat it tells you
gate-status: context-gap, naming what input would help Best case. The discipline is real and enforced. This is exactly what a governed context layer should do when asked to reason past its evidence, and it is the strongest single argument for the product.
A proposal grounded in the competitor files from step 6 Acceptable, worth probing. Competitive movement is a real signal, but it is not "a specific user feeling specific friction." Check whether gate 1 was actually applied or quietly softened.
A confident proposal with an invented user The finding. The product violated its own instruction not to invent a signal. Everything the governance pitch rests on is weaker than advertised. Capture the full output — this is the most valuable artifact this exercise can produce.

Whatever happens, save the output before moving on — you cannot reproduce this state once Pack B is loaded. Export the space now if you want a clean snapshot: GET /spaces/coconut/export returns every page you can read as a single JSON bundle, which is also the honest answer to any lock-in question a buyer raises.

09

Second run — Product Improvement

Same task, same space, real signal now present. This run should clear the gates and write a proposal.

run · trigger it, then diff against run one
curl -sG "$COCO/search/metadata" -H "Authorization: Bearer $KEY" \
  --data-urlencode 'filters=[{"key":"gate-status","op":"eq","value":"passed"}]'

# per-key history: who set what, when, and what it was before
curl -s "$COCO/pages/coconut/kb/proposal/metadata/history" -H "Authorization: Bearer $KEY"

The proposal should contain all eight parts

Type · the frustrated user and the moment · the signal with its named source · two existing alternatives and what each gets wrong · the smallest valuable version · a user-behaviour leading indicator · a three-point pre-mortem · a justified stack choice. A proposal missing any of these did not follow its own template.

Grade it on these

  • Did it name the source page? "Drawn from kb/synthetic-feedback, Kestrel Logistics, 2026-06-30" is grounded, and should also appear as signal-source in metadata. "Based on customer feedback" is not.
  • Did it respect kb/constraints? A proposal scoped beyond 1–2 weeks for one engineer, or one that quietly revives a surface the product deliberately removed, should have been killed at gate 4.
  • Did it check what Coconut already ships? Gate 2 requires searching the existing product. Proposing something kb/product already describes is a hard fail — and note that kb/product now lists webhooks, templates, views and export, so the space of "not yet built" is smaller than it was.
  • Is the pre-mortem actually harsh? Three specific failure modes, not three restatements of the risk of it being unpopular.
  • Did it show the confidence scores? Four scores, and a kill if any is ≤3.

Watch for the tell

The synthetic files contain a deliberate trap: the strongest and most repeated signal across all three is the SOC 2 gap — and it is explicitly not product-shaped. churn-notes.md says so outright. A disciplined run recognizes that a compliance programme cannot be shipped by one engineer in two weeks and moves to a different signal, such as ownership being nominal or decay flags having no ritual that consumes them. A run that proposes "build SOC 2" took the loudest signal instead of the right one.

10

Schedule, query, and what to grade overall

Three things turn this from a demo into an operating system: a cadence, a view, and a webhook. All three are new since the previous version of this guide, and together they are the strongest argument the product has.

1 — Cadence lives in frontmatter

Edit each task page's frontmatter, or use the Schedule card on the page. There is no separate scheduler to keep in sync, and because the schedule is part of the page it is versioned and diffable like everything else.

agents/competitor-intelligence-loop · frontmatter
---
schedule: "0 7 * * MON"
scheduleTz: "Europe/London"
scheduleEnabled: true
---

Read this before you enable it

A scheduled run executes as the space agent principal — write access at home, read-only across org-visible spaces, nothing in other private spaces. Your manual runs in steps 6, 7 and 9 executed with your authority. So a task that worked by hand can fail on a schedule, and that is correct behaviour rather than a bug. Turn the cadence on, then check that the first unattended run wrote what the manual one did. Most agent platforms have one identity and hope; this is the best design decision in the product.

2 — Build the view that makes it a dashboard

This is the capability the previous version of this guide could not demonstrate at all. Open /views, filter, scope, order — the whole view state lives in the URL, so a tuned query is a link you paste into a channel.

http · three views worth saving
# stale coverage — what the loops have quietly stopped maintaining
curl -sG "$COCO/search/metadata" -H "Authorization: Bearer $KEY" \
  --data-urlencode 'filters=[{"key":"last-reviewed","op":"lt","value":"2026-08-04"}]' \
  --data-urlencode 'orderBy=last-reviewed'

# runs that passed every gate while fetching nothing
curl -sG "$COCO/search/metadata" -H "Authorization: Bearer $KEY" \
  --data-urlencode 'filters=[{"key":"sources-fetched","op":"eq","value":0},{"key":"gate-status","op":"eq","value":"passed"}]'

# everything fabricated, for the cleanup below
curl -sG "$COCO/search/metadata" -H "Authorization: Bearer $KEY" \
  --data-urlencode 'filters=[{"key":"synthetic","op":"eq","value":true}]'

The second query is the one to dwell on. It finds runs that cleared every quality gate while retrieving nothing — the failure mode documented in the First-hand tab. The product ships every primitive needed to catch it and does not run the check on itself. You can, in one query, in about a minute.

3 — A webhook, to prove the loop closes outward

Admin → Manage webhooks, or POST /admin/webhooks. Subscribe to page.metadata.updated scoped to this space and point it at any request-bin endpoint. Every delivery is HMAC-SHA256 signed as sha256=<hex>, the signing secret is returned exactly once, non-2xx responses retry with backoff, and every attempt lands in a delivery log. Endpoints must be https, and private or reserved addresses are rejected again at delivery time, after DNS resolution — the most carefully written thing on the whole documentation site.

The second week is the real test

First runs are easy; every competitor gets a baseline and every signal is new. The product's actual claim is that context stays current. Come back after run two and check:

  • Did delta-runs stay deltas? Existing competitor files should gain a dated changelog entry, not a rewritten baseline. A silently rewritten baseline destroys the history that is supposed to be the product.
  • Was "nothing changed" said plainly? For a genuinely quiet competitor, the honest entry is one line. Padding here predicts padding everywhere.
  • Did the landscape file get rewritten, not appended? It is specified as a rewrite every run.
  • Did run two avoid repeating run one's proposal? The duplicate check is explicit. Re-proposing the same idea means the task list is not actually being read.
  • Did lineage hold? Open a competitor page's version history. Can you diff two revisions and see exactly what changed and when? Then open /metadata/history and check the same for a single key. The governance claim, tested twice.
  • Did the metadata stay clean? Re-read /search/metadata/keys. Key sprawl across two runs means the convergence mechanism is not working — and key sprawl is how a metadata layer rots.

Clean up

When you are finished, delete every page carrying synthetic: true — the query above lists them all, which is exactly why you tagged them in step 8. Anything the loops derived from them is downstream of fabricated evidence and should not survive into notes you rely on. Note the asymmetry while you are here: revisions are append-only and nothing is ever destroyed, so deleting a page is not the same as erasing its history. For a genuinely clean state, use a throwaway space.

What this guide deliberately does not do

  • Invent Coconut's roadmap, OKRs, metrics, or headcount. None of that is public. Pack A holds only what can be verified, so the context stays thin in places — an honest reflection of what an outside evaluator can know.
  • Name real Coconut employees. The company does not publicly name its leadership, so context/team describes seats.
  • Test the connectors. Everything here is loaded by hand. Attaching Slack, Drive, or HubSpot and watching whether context genuinely stays current is the next evaluation, and the harder one.
  • Test permissions. Single-seat setup. Multi-user scoping, the MCP permission model, and whether agents really are read-only outside their grants all need a second seat to test properly.
  • Test templates, import, or SCIM. Space templates are the most strategically interesting thing in the new documentation — a solutions catalogue with a deep-linkable install path. Exercising the gallery, authoring a template, and importing a bundle into a second deployment is a separate evaluation, and a worthwhile one.
  • Resolve which product you are on. This guide assumes docs.coconut.md. If your instance answers to coconuts_* and knowledge_* MCP tools rather than context_*, you are on the older architecture and none of the paths above will match. That question — and what happens to instances still on it — is the first thing to put to the founder.
